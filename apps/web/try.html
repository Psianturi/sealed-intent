    What SeIn looks at

    • The receiverDoes the account exist? How old is it? Is it a contract?
    • The paying account's historyHas it paid this receiver before? Does the name pass for one it has paid?
    • The amountIs it unusual for this account, or most of its balance?
    • The messageDoes it use pressure, secrecy or an order to ignore rules?

    A pass needs a receiver the paying account has paid before. Anything SeIn cannot confirm is a warning, never a pass.

    13 Nov 2026, NEAR mainnet. The same checks stood in front of a custody wallet with real NEAR: a trick was refused and a 0.005 NEAR invoice was paid. See it read from the chain

    What this is, and what it is not

    Real data

    Every fact is read live from NEAR: the account, its age, the paying account's recent payments and its balance.

    Private

    No wallet connection and no key. The message is read inside an enclave, and nothing about the check is kept.

    Advice, not a lock

    Here SeIn cannot stop a payment; you decide. In front of an agent's wallet the same checks are a hard stop.

    For agents too

    An agent can ask the same question over HTTP before it pays: one request with the receiver, the payer and the amount.

    A clean answer is not a guarantee: an account you have paid before can still be the wrong one today. NEAR payments only, for now.
